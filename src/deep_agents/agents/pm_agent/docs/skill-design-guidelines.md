# PM Agent Skill 设计与加载原则

## 核心定位

PM Skill 不是项目管理流程脚本，也不是工具说明书。

Skill 的作用是在**特定项目情境**下，为 PM 提供额外的判断经验、风险信号和决策边界。

Skill 应增强模型判断，而不是替代模型思考。

## 基础 Prompt 与 Skill 的边界

基础 Prompt 负责长期稳定、几乎所有项目都需要的原则，例如：

- PM 是项目治理者，而不是普通 Worker。
- 目标优先于任务列表。
- 证据优先于状态声明。
- 区分事实、假设和未知信息。
- 计划服务于目标，可以因新事实调整。
- 不为了记录而制造文档。

这些原则不应该包装成一个几乎始终会被加载的通用 Skill。

Skill 只负责**特定状态下才有价值**的判断增强。

## 当前 Skill 边界

- `goal-understanding`：目标、边界或成功标准还不够清楚。
- `planning`：目标基本明确，需要决定推进路线。
- `progress-review`：项目正在推进，需要判断真实状态和下一步。
- `failure-diagnosis`：出现失败、阻塞或重复无效尝试，需要判断根因。
- `replanning`：关键事实变化，原路线已经不再合理。
- `acceptance-review`：准备关闭或交付，需要判断结果是否足够。
- `retrospective`：阶段结束或关键结果出现，需要提取未来可复用经验。

## 加载原则

Skill 默认按需发现和加载，不预加载全部内容。

`description` 应优先表达**什么时候需要这个 Skill**，包括典型触发信号和与相邻 Skill 的边界，让模型在读取正文前就能判断相关性。

如果多个 Skill 都可能相关，只加载对当前决策真正有帮助的最小集合。

一个事件可能先后触发不同 Skill。例如失败可能先进入 `failure-diagnosis`，只有当诊断表明路线失效时才进一步使用 `replanning`。

## 内容设计

好的 Skill 应尽量包含：

- 触发场景或触发信号。
- 这个场景最容易出现的误判。
- 值得关注的判断维度。
- 与相邻 Skill 或基础 Prompt 的边界。
- 少量高价值约束。

不要求固定章节或统一模板；内容应服从实际判断价值。

## 保持模型自由度

避免：

- 固定输出模板。
- 强制生成大量文档。
- 固定步骤数量。
- 把所有情况写成决策树。
- 为了“完整”穷举所有可能性。
- 用大量规则替代模型对上下文的理解。

如果一个 Skill 只是在重复常识或基础 Prompt，它不值得单独存在。

## 质量标准

判断一个 Skill 是否值得保留，优先看：

- 是否能在特定场景提高判断质量。
- 是否减少一种真实、重复出现的错误。
- 是否包含模型不一定会主动注意到的经验。
- 是否有清晰触发边界，不会几乎每次都加载。
- 是否保持足够自由度，让模型能适应不同项目。

Skill 的质量不由长度、步骤数量或文档复杂度决定。
