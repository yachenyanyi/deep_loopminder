# 目标理解

目标理解不是把需求改写得更漂亮，而是确认项目最终要产生什么结果，以及什么证据能说明这个结果已经实现。

## 关注

- 真正希望改变的结果是什么，而不是“要做哪个功能”。
- 谁会使用或依赖这个结果，他们在意什么。
- 什么现象或证据可以说明目标达成。
- 哪些约束是真实存在的：时间、资源、兼容性、权限、范围等。
- 哪些内容明确不是当前目标，避免范围自然膨胀。
- 当前哪些判断是事实，哪些只是方案、偏好或假设。
- 哪些未知信息会真正改变路线，哪些不会。

## 判断边界

不是所有不确定性都需要停下来追问。

如果某个未知信息会显著改变目标、成本、风险或验收标准，应优先澄清。

如果影响较小、容易回退，可以明确采用临时假设继续推进，并保留验证点。

## 避免

- 把用户提出的实现方式直接当成最终目标。
- 目标还没有基本边界就开始大规模拆任务。
- 为了“需求完整”追问所有细节，导致项目无法启动。
- 静默补全关键假设，让后续偏差看起来像执行失败。
